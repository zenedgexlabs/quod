# E8: The agent loop, end to end through MCP

**Question:** when a coding agent follows Quod's MCP answers, calling
`tests_for` and running the command it returns instead of the whole
suite, does it still see every failure its change causes? And how much
does it run?

**Method** (`conformance/agent_loop.py`). A map is recorded at a real
commit G. Then, for each of the next ten real first-parent commits C:

1. The repository is left the way an agent leaves it: HEAD at C's parent
   and C's change uncommitted in the working tree. Odd steps add a
   mutant (as in E1) on top, standing in for an agent's bug.
2. `tests_for` is called through `quod mcp` over stdio, as an agent calls
   it. Environment mode comes from detection (`QUOD_PYTHON`), not flags.
3. The returned `run` command is executed exactly as returned, plus
   `--quod-results`.
4. The full suite runs on the same tree. That run is the ground truth.

The scoring:

- **Escape:** a test fails in the full run and fails alone three times,
  but the returned command didn't run it.
- **Missed collection error:** the full suite couldn't be collected (a
  broken import) and the returned command still exited 0. This also
  counts as an escape.

The gate is 0 escapes.

The map stays at G for all ten steps, so by the last step it is nine
commits behind HEAD. Selection compares the working tree with the map's
commit, so later steps also re-run the tests for earlier steps' changes.
CI publishes a map for every green commit, so the map an agent pulls is
usually 0 to 2 commits behind. These fractions are therefore a
pessimistic bound.

## Results (2026-11-26, Windows, Python 3.13, environment mode)

| repo | steps | failing tests (full run) | caught by the returned command | escapes | tests run | time |
|---|---|---|---|---|---|---|
| itsdangerous | 10 | 250 | 250 | **0** | 61% | 77% |
| attrs | 10 | 13, plus 1 collection error | 13, plus the error (exit 2) | **0** | 35% | 51% |
| more-itertools | 8 | 18 | 18 | **0** | 82% | 45% |

In more-itertools, two mutant steps were dropped because the suite hangs
under them (the timeout is 10× the baseline suite time). No test that
failed in the full run passed in the returned command's run, so there
were no order-dependent victims.

**Where the time goes.** In attrs, a typical code change ran 7 to 74 of
1,411 tests in 1.5 to 5 s instead of 11 to 14 s. Two kinds of step ran
everything:

- A commit that edits `__all__` in `attr/__init__.py`. Every test imports
  that module, and star-imports make `__all__` behavioural, so this is
  deliberate.
- Steps whose diff from the old map still contained that edit.

In more-itertools the tests skipped are the slow ones: 82% of the tests
took 45% of the time. itsdangerous's whole suite takes about 2 s, so
pytest start-up dominates.

**What this does not cover.** Every step ran in the environment the map
was recorded in. When the agent's environment differs from CI's (another
OS, interpreter or package set), Quod runs every test (rule R018) and
says why. That is sound, and it saves nothing. A real LLM agent working
on tasks is E8b. The harness drives pytest repositories only.
