# E9: Quod on GitHub-hosted CI

**Question:** with the published GitHub Action on GitHub's own runners,
does a pull request still catch every failure its change causes? How much
of the suite runs, and what does a pull request's test step cost?

**Method** (`conformance/ci_replay.py`). Each repository is forked under
`zenedgexlabs`, and its workflows are replaced with one Quod workflow
that uses the Action (`ci_replay.py --print-workflow` shows it; the run
below used `quod-version: v0.1.0-alpha.3`). The fork's `main` starts at the commit
where E8 records its map. Then, for each of the next ten real first-parent
upstream commits C:

1. A pull request gets C's exact tree. On odd steps it also gets a mutant
   (as in E1), standing in for a bug.
2. The pull request runs two jobs on the same commit:
   - **shadow** runs the full suite and reports what Quod would skip;
   - **enforce** runs only what Quod doesn't skip.
3. C (without the mutant) lands on `main`. As after a real merge, the push
   records the map the next pull request is compared with.

Scoring:

- **Escape:** a test that shadow mode would skip but that failed in
  shadow mode's full run. The gate is 0.
- **Time:** the duration of the Action's step in each job. That covers
  installing Quod and the probe, planning, the tests and the Verdict: what
  a pull request pays. GitHub reports it in whole seconds.

## Results (2026-11-27, `ubuntu-latest`)

| repo | runner | steps scored | failing tests (full run) | caught by enforce | escapes | tests run | Quod step, enforce vs shadow |
|---|---|---|---|---|---|---|---|
| ufo | Vitest | 10 of 10 | 41 | 41 | **0** | 32% | 55 s vs 62 s (median step 93%) |
| more-itertools | pytest | 9 of 10 | 24 | 24 | **0** | 41% | 74 s vs 221 s (median step 43%) |

**0 escapes in 19 scored pull requests, 65 of 65 failing tests caught.**

- **more-itertools.** A pull request's Quod step took 6 to 14 s with
  enforce, against 14 to 80 s with shadow. Two mutants make the suite
  hang. Step 1's mutant made it slow but it finished: both jobs ran all
  769 tests, because the change touches `recipes.sieve`, which every test
  reaches. Step 3's mutant hung
  both jobs until the 20-minute timeout, so it has no results and isn't
  scored. Both are left out of the time column.
- **ufo.** The suite itself takes about a second on a runner, so the Quod
  step (5 to 8 s) is mostly installing Quod and the probe. Quod ran 32% of
  the tests: steps 1, 3 and 6 update the test toolchain's dependencies,
  which correctly runs everything, and most other steps run 0 to 38 tests.
  As in E8, a suite this fast gains a certificate for each skip, not
  speed.
- **The tests-run column counts shadow's plans.** In more-itertools
  step 7 the two jobs disagreed: enforce skipped 764 of 771 tests, and
  shadow ran all of them because its runner's kernel release differed
  from the one the map was recorded on (R018, `system.os_release`).
  GitHub's runners don't all run the same kernel. That happened in 1 of
  38 jobs. It's sound (the environment really differs), and it costs a
  full run now and then.

## What E9 found

E9 is the first time the Action ran on hosted runners against real
history. Each of these was found by it and fixed before the run above.

- **The map inside the checkout.** The Action kept the map in
  `.quod/`, so the pull request's change included the map itself, which
  is Quod policy (R004), and every test ran. The map now lives in the
  runner's temp directory, and `quod select` ignores the map's own path.
- **pytest's cache as a test input.** `.pytest_cache` and `__pycache__`
  were recorded as files tests depend on, so a fresh checkout looked like
  a change. The probe now ignores the runner's own state.
- **No Verdict when tests failed.** The Action's shell stopped at the
  failing test command (`bash -e`), so a failing pull request, the case
  where the Verdict matters most, got no Verdict and no artifacts. Both
  steps now always run, and the job still fails.
- **Hung mutants.** Two mutants make a test loop forever; with no job
  timeout they held runners for six hours. The workflows now set
  `timeout-minutes: 20`.
- **A stale map in the harness.** The first version compared every pull
  request with the map from step 0, as E8 does. Real CI records a map on
  every merge, so the harness now lands each step on `main` first.

## Reproducing

```sh
cd conformance
uv run python ci_replay.py --repo more-itertools --window 10 --push   # needs gh, forks under --owner
uv run python ci_replay.py --repo more-itertools --collect            # writes results/e9-more-itertools.json
```

`conformance/results/e9-<repo>.json` has each replay's scores per step,
and `e9-index.json` lists every replay. The per-step artifacts (plans,
skip files, per-test results, Verdicts) are archived, one release per
run, in [zenedgexlabs/quod-replays](https://github.com/zenedgexlabs/quod-replays/releases);
each summary links its archive and SHA-256. The pull requests and runs stay public
on [zenedgexlabs/ufo](https://github.com/zenedgexlabs/ufo/pulls?q=is%3Apr)
and
[zenedgexlabs/more-itertools](https://github.com/zenedgexlabs/more-itertools/pulls?q=is%3Apr).
